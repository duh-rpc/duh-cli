RS-001 · MEDIUM · Resolved (was: deferred)

Fix applied (commit faaf92b): the shared validator now errors when x-duh-did-you-mean is declared on a path item with no post: operation, naming the path (message: "…must sit beside a post: operation; this path item has none"). Chosen resolution: error, per the author. Proving test TestDidYouMeanOnOperationlessPathItemErrors un-skipped and passing.

A teaching path declared on a path item that produces no generated operation is silently discarded.

Found bycode-review (Phase 1)
Stagereview-validate (Phase 2)
Locationinternal/generate/duh/parser.go:142 (resolveDidYouMean only reached for surviving ops) vs parser.go:341 (ValidateDidYouMean walks every path item)
Proving testTestDidYouMeanOnOperationlessPathItemIsNotSilentlyDropped (skipped) — did_you_mean_review_test.go:79
InvariantBlueprint: "For each declared path, the switch gains one arm."

Summary — ValidateDidYouMean validates the x-duh-did-you-mean entries on every path item, but the teaching case arms are only emitted for path items that survive extractOperations. A path item that carries the extension but produces no operation (e.g. it has no post:) passes validation cleanly and is then dropped — generation exits 0 with no arm and no diagnostic.

Explainer — When duh generate parses a spec, extractOperations() (parser.go:89) skips any path item where pathItem.Post == nil (parser.go:102) and also skips items whose request/response types don't resolve. Only for the survivors does it call resolveDidYouMean(base, pathItem) (parser.go:142) to attach the teaching paths to that operation record, which the template later turns into case arms.

Independently, ValidateDidYouMean(spec) (parser.go:341) iterates all path items to check for collisions and malformed entries. So the two passes see different sets of path items. If an author writes the extension on a path item with no post: operation — a plausible mistake, e.g. attaching the guess table to the wrong path, or to a GET-only stub — ValidateDidYouMean sees it (finds no collision, so no error), but extractOperations never reaches resolveDidYouMean for it. The declared guess never becomes a route.

The failure scenario, step by step: a spec has /widgets.create (valid POST) and a second path item /widgets.get carrying only x-duh-did-you-mean: [/widgets.fetch] and no operations → duh generate prints ✓ and exits 0 → the generated server.go contains no reference to /v1/widgets.fetch. The author believes /v1/widgets.fetch now teaches; it does not. Blast radius: any spec that declares the extension on a path item that doesn't generate an operation — the guess is neither taught nor reported.

Correct behavior is a judgment call, which is why this was deferred: either (a) emit the teaching arm anyway (the literal "each declared path gains one arm" contract), or (b) fail generation naming the offending path (a path item with the extension but no operation is arguably itself a spec error). What is not acceptable is the current silent success.

Evidence

--- FAIL: TestDidYouMeanOnOperationlessPathItemIsNotSilentlyDropped
    exit code 0, generated server.go does not contain "/v1/widgets.fetch"
    (switch has only: case RPCWidgetsCreate; no teaching arm emitted)

Repro (remove the t.Skip first): go test -run '^TestDidYouMeanOnOperationlessPathItemIsNotSilentlyDropped$' ./internal/generate/duh/...

Why it wasn't auto-fixed — the correct resolution (emit vs. error) is a design decision about how duh generate should treat the extension on a non-generating path item. The suite took the safe default: leave the proving test red (skipped), report, change no behavior.

Suggested fix — decide the policy, then enforce it in one place. If erroring: in ValidateDidYouMean, when a path item declares the extension, verify it also has a generated operation (mirror the extractOperations filters) and add a problem naming the path if not. If emitting: hoist teaching-path resolution out of the per-operation loop so it runs for every path item that declares the extension. Given RS-004 (duplicated validators), enforce it in the shared location once that consolidation happens. Remove the t.Skip at did_you_mean_review_test.go:79 after applying (adjust the assertion to match the chosen policy).

RS-002 · MEDIUM · Resolved (was: deferred)

An entry containing characters that can't appear in a Go string literal passes validation and breaks template rendering with an opaque error.

Found bycode-review (Phase 1)
Stagereview-validate (Phase 2)
Locationparser.go:370 & did_you_mean_collision.go:73 (only leading-slash checked) → server.go.tmpl:66 (raw interpolation into case "…")
Proving testTestDidYouMeanUnsafeEntryIsRejectedByName (skipped) — did_you_mean_review_test.go:363
InvariantBlueprint acceptance: "duh generate exits non-zero, naming the offending path, when a did-you-mean entry is malformed."

Summary — both validators check only that an entry is a string beginning with /. An entry like /widgets".injected passes, then the template interpolates it verbatim into case "{{$teach}}":, producing invalid Go. Generation fails — but with an opaque template-render error that does not name the entry, instead of the clean, named "malformed" rejection the blueprint promises.

Explainer — The teaching arm is generated by server.go.tmpl:66-69, which emits case "{{$teach}}": where $teach is the full teaching path, interpolated with no escaping. Both ValidateDidYouMean (parser.go:364-373) and its lint twin (did_you_mean_collision.go:61-82) accept any YAML scalar string whose value starts with /. Neither rejects an embedded double-quote, backslash, or newline.

Failure scenario: a spec declares x-duh-did-you-mean: ['/widgets".injected'] on an otherwise-valid POST path → validation passes → the template renders case "/widgets".injected":, which is not valid Go → generation aborts with error: failed to render server.go: 46:29: string literal not terminated (and 10 more errors). No file is corrupted (generation buffers before writing), so this is not a code-injection or bad-output bug — but the acceptance criterion that a malformed entry is rejected by name is violated: the author gets an internal template error pointing at a generated-source line, not their spec.

Blast radius: any hand-authored spec whose teaching entry contains a character illegal in a Go string literal. Low probability (real URL paths rarely contain "), bounded impact (safe failure, confusing message).

Why it wasn't auto-fixed — the blueprint's definition of "malformed" is only "non-string, or not starting with /." Suggested fix — add a character check to the shared entry validation. Minimal, defensible rule:

The did-you-mean validation is implemented twice — once for generate, once for lint — with no shared code.

Found bycode-review (Phase 1, both reviewers)
Locationinternal/generate/duh/parser.go:341-411 ↔ internal/lint/rules/did_you_mean_collision.go:29-131; duplicated sortedKeys at parser.go:406 and did_you_mean_collision.go:124
InvariantBlueprint: "Generate does not depend on lint having run; it enforces independently."

Summary — ValidateDidYouMean and DidYouMeanCollisionRule.Validate are near-verbatim copies of the same three-constraint validation (well-formed, no canonical collision, declared once), plus an identical private sortedKeys. They agree today, but nothing links them — a future fix to one can silently diverge from the other.

Explainer — Independent enforcement (generate not depending on lint) is a deliberate blueprint decision, so some duplication of the invocation is expected. The concern is the duplication of the logic itself. This is not hypothetical: the same real gaps (RS-001, RS-002) exist identically in both copies, and RS-003 had to be fixed in both places. A direct import can't remove it — internal/generate/duh already imports internal/lint (duh.go:9), so the lint rule can't call back into the generator without an import cycle.

Why it wasn't auto-fixed — consolidation requires introducing a third shared package (e.g. internal/didyoumean) that both the generator and the lint rule import, and deciding its API surface. That is a structural refactor and a design call, not a mechanical fix.

Suggested fix — extract the entry-parsing + three-constraint check into one small package returning structured problems; have ValidateDidYouMean format them as an error and the lint rule map them to Violations. Fold the RS-001/RS-002 fixes into that single implementation. No test change required beyond the existing generate + lint coverage, which will then exercise one code path.
