fieldmap.lock — the three decisions

Tech-spec deep dive · duh-cli · candidates for ADRs

All three decisions share one root cause: Protobuf field numbers are wire-critical and must never change for a field once published, but OpenAPI field order is meaningless. fieldmap.lock pins the mapping. These three choices decide how the numbers get injected, how removals are recorded, and what identifies an enum variant.

Decision 1 ADR candidate

How locked numbers reach the generated proto

Inject resolved numbers as a structured FieldNumbers argument to the conversion library — not by writing numbers into the OpenAPI spec, and not by rewriting proto text after the fact.

The problem

duh-cli does not assign field numbers itself. It hands the OpenAPI bytes to the openapi-schema.go library, which builds the proto. Numbering lives inside that library's internal package (not importable) and is purely positional:

// inside the library's builder — today
fieldNumber := 1
for propName := range schema.Properties.FromOldest() {
    field.Number = fieldNumber  // position decides the number
    fieldNumber++
}

So inserting a field mid-schema silently renumbers everything after it. We need the lock to decide numbers instead of position. Three ways to make that happen:

OptionHowWhy not
(a) In-spec x-proto-number The library already reads an x-proto-number extension on each property. duh-cli could write numbers into the spec before conversion. Pollutes the author's spec with numbers the lock is meant to own; all-or-nothing per schema; no enum support; no reserved. And Convert() takes raw bytes, so we'd have to re-serialize mangled YAML.
(b) Proto-text post-process Let the library emit positional proto, then rewrite each = N using the json_name annotation as a join key. A fragile text layer over an external output format; re-derives nothing the library already knows; breaks the moment proto formatting shifts.
(c) Structured FieldNumbers Add an optional, typed field-number map to the library's options. When present it overrides positional numbering and emits reserved. You own the library. The contract is data, not text. Covers messages, enums, and reserved uniformly. Back-compatible (nil = today's behavior).

What it looks like

The library gains one optional field. nil keeps every existing (non-duh) consumer working exactly as before:

type ConvertOptions struct {
    PackageName   string
    PackagePath   string
    GoPackagePath string
    FieldNumbers  *FieldNumbers // NEW — nil ⇒ positional numbering
}

type FieldNumbers struct {
    Messages map[string]MessageNumbers // key: OpenAPI schema name
    Enums    map[string]EnumNumbers    // key: OpenAPI schema name
}
type MessageNumbers struct {
    Fields   map[string]int // key: JSON field name → proto number
    Reserved []int         // rendered as `reserved N;`
}

The three map keys are OpenAPI-native and join cleanly to fields the library already tracks — no new name-derivation, no guessing:

Lock keyJoins to (library)
message → OpenAPI component schema nameProtoMessage.OriginalSchema
field → JSON field nameProtoField.JSONName
enum variant → literal enum valueenum value.Value

The flow, end to end

duh generate users.yaml
   │
   ├─ load + lint (spec rules only)
   ├─ fieldmap.Reconcile(spec, existingLock)  ──▶  lock + *FieldNumbers
   ├─ converter.Convert(specBytes, …, FieldNumbers)
   │        └─ library numbers by NAME, ignores declaration order, emits reserved
   └─ write proto + code + fieldmap.lock   (atomically, only if all succeeded)
Why it's ADR-worthy. Hard to reverse (it defines the library's public contract and forces the migration off openapi-proto.go); surprising without context (a future reader will ask "why a typed option and not the x-proto-number that's already there?"); a real trade-off against two working alternatives.

Decision 2 ADR candidate

How removed fields are recorded — tombstones

When a field is removed, keep its entry in the lock with reserved: true, retaining the original name→number binding — rather than moving the bare number into a separate reserved: [N] list.

Reserved numbers are permanent (ADR 0002): once a number is used it is never reassigned, because old wire data may still carry it. The question is purely how the lock file records that fact.

Worked example

Start with three fields, then remove nickname and add displayName:

CHOSEN — tombstone entry

messages:
  CreateUserRequest:
    fields:
      name:        {number: 1}
      email:       {number: 2}
      nickname:    {number: 3, reserved: true}
      displayName: {number: 4}

The name nickname and its number 3 stay together, flagged dead. The next number is 4, never 3.

REJECTED — bare reserved list

messages:
  CreateUserRequest:
    fields:
      name:        {number: 1}
      email:       {number: 2}
      displayName: {number: 4}
    reserved: [3]

The number 3 survives, but which field held it is gone. The diff just shows a bare 3 appearing.

Why tombstones won

The PRD's primary guard against a bad hand-edit is the reviewable diff — "treat a surprising lock diff like a surprising go.sum diff." Compare what a reviewer sees when nickname is removed:

# tombstone diff — self-explanatory
-     nickname: {number: 3}
+     nickname: {number: 3, reserved: true}

# reserved-list diff — needs archaeology
-     nickname: {number: 3}
+   reserved: [3]   # reviewer must remember 3 *was* nickname
Tombstone (chosen)Reserved list (rejected)
Removal historyPreserved — name→number stays visibleLost — only the number remains
Diff readability"nickname became reserved""3 appeared in a list"
Lint reserved-retention checkReads tombstones directly as authoritativeReads the list — also fine
File compactnessSlightly busierTighter
Mirrors proto's own reservedNo (richer)Yes

Note: the library still receives a flat Reserved: [3] list inside FieldNumbers — duh-cli flattens tombstones into that list at conversion time. The tombstone is the file representation; the list is the wire to the library.

Rename is "remove + add" — tombstones shine here too

Renaming nickname → handle: the old name is tombstoned, the new one gets the next number. The lock literally tells the story:

      email:    {number: 2}
      nickname: {number: 3, reserved: true}   // was here
      handle:   {number: 4}              // is now here
Why it's ADR-worthy. Hard to reverse (it's a committed file format — locks in the wild encode it); surprising (a reader expecting proto-style reserved [3] will wonder why entries linger); a real trade-off (compactness & proto-symmetry vs. diff-reviewability — and we deliberately chose reviewability).

Decision 3 ADR candidate

What identifies an enum variant — the literal value

Key each enum variant on the literal string from the spec's enum: list (e.g. "active"), not the derived proto constant (STATUS_ACTIVE).

The two candidates

A DUH spec declares the sentinel first (ADR 0004):

Status:
  type: string
  enum: [STATUS_UNSPECIFIED, active, inactive, suspended]

CHOSEN — literal value as key

enums:
  Status:
    variants:
      STATUS_UNSPECIFIED: {number: 0}
      active:             {number: 1}
      inactive:           {number: 2}
      suspended:          {number: 3}

REJECTED — proto constant as key

enums:
  Status:
    variants:
      STATUS_UNSPECIFIED: {number: 0}
      STATUS_ACTIVE:      {number: 1}
      STATUS_INACTIVE:    {number: 2}
      STATUS_SUSPENDED:   {number: 3}

Why the literal value

  • It's the JSON-wire identifier. On the JSON wire the variant name — "active" — is what's transmitted. The lock's whole job is to map the JSON world to proto numbers, so the JSON-side key should be the JSON-side string.
  • It's stable under proto-name-derivation changes. The constant STATUS_ACTIVE is computed from the schema name + value (ToEnumValueName("Status", "active")). If the enum schema is renamed, or the derivation rule changes, every constant key shifts — and a shifted key reads as "old variant removed, new variant added," tombstoning live numbers. The literal "active" never moves.
  • No derivation needed to validate. Lint and reconcile read the literal straight from value.Value; keying on the constant would force them to re-run the library's naming logic just to match entries.

The failure the constant key invites

Suppose someone renames the schema Status → UserStatus. The proto constants become USER_STATUS_ACTIVE, etc. Watch what each key does:

# literal-value key — survives the rename, numbers intact
  active: {number: 1}        →   active: {number: 1}   ✓

# constant key — every variant looks removed + re-added
  STATUS_ACTIVE:      {number: 1}
  → tombstoned as reserved, and:
  USER_STATUS_ACTIVE: {number: 5}   ← silent renumber of a live variant

That is exactly the silent renumbering this entire feature exists to prevent — so the key must not be coupled to a derived name.

Why it's ADR-worthy. Hard to reverse (committed locks encode the key choice); surprising (the ADRs discuss *_UNSPECIFIED in constant form, so a reader might assume constants are the key); a real trade-off (constant keys read more "proto-native," but we chose JSON-wire stability).
