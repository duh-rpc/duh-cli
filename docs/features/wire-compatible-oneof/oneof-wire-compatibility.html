Unions on the wire in DUH-RPC

How a union serializes decides whether DUH can use it — because the same schema is served as both JSON and protobuf. Here's the why, the what's-allowed, and the proof.

The whole idea in one sentence. DUH-RPC serves the same OpenAPI schema as both application/json and application/protobuf. So a union is usable only if a single schema can describe it truthfully on both wires — and that is true for exactly one JSON shape: the nested, key-tagged one.

1. The two wire formats don't match

Model an event that is either a cat or a dog. The obvious OpenAPI modelling — a discriminated oneOf — and the obvious protobuf modelling — a oneof — describe the same idea, but they put different bytes on the JSON wire for the same value.

OpenAPI discriminated oneOf → JSON

oneOf:
  - $ref: '#/.../CatEvent'
  - $ref: '#/.../DogEvent'
discriminator:
  propertyName: type
  mapping: { cat: ..., dog: ... }
↓ on the wire ↓
{ "type": "cat", "pet_name": "Whiskers" }

FLAT The variant's fields are hoisted to the top level; the discriminant is the value of a tag property.

Protobuf oneof → proto3 JSON

message Event {
  oneof kind {
    Cat cat_event = 1;
    Dog dog_event = 2;
  }
}
message Cat { string pet_name = 1; }
↓ on the wire ↓
{ "cat_event": { "pet_name": "Whiskers" } }

NESTED The set variant is nested under its field name; the discriminant is which key is present. There is no separate tag.

Why protobuf simply cannot produce the flat shape. proto3 has no "inline" or "flattened" oneof. A oneof is always serialized by emitting the single set field under its own name, with its value nested. There is no language construct that lifts a variant's fields up to the parent object and adds a discriminator string. So the flat shape is unreachable from a .proto — this is structural, not a tooling gap. A DUH schema that produced the flat JSON could never be honestly served as protobuf.

2. The union shape that does work on both wires

Flip it around. Instead of a discriminated oneOf, describe an object with one optional property per variant. Now the OpenAPI JSON and the protobuf JSON are the same bytes — because both are nested and keyed by the variant name.

OpenAPI — optional properties

Event:
  type: object
  properties:
    cat_event: { $ref: '#/.../Cat' }
    dog_event: { $ref: '#/.../Dog' }
↓
{ "cat_event": { "pet_name": "Whiskers" } }

Protobuf — oneof (or plain optionals)

oneof kind {
  Cat cat_event = 1;
  Dog dog_event = 2;
}
↓
{ "cat_event": { "pet_name": "Whiskers" } }

SAME BYTES The key (cat_event) is the discriminant on both sides. A protobuf oneof with one field set serializes identically to optional message fields with one field set — and identically to what a generic JSON client writes.

So the takeaway: a compatible union is one whose JSON is nested and key-tagged. DUH supports that shape; it does not support the flat, value-tagged shape that a discriminated oneOf produces. The rest of this page is the precise rules and the proof.

3. The two union styles DUH supports

Both produce the identical nested wire shape from §2. They differ only in whether the schema also declares the variants mutually exclusive. Pick by how strict you want JSON-Schema validation to be — the bytes on the wire are the same either way.

A · Optional-properties union no oneOf

Event:
  type: object
  properties:
    cat_event: { $ref: '#/.../Cat' }
    dog_event: { $ref: '#/.../Dog' }
  • One optional $ref property per variant.
  • Validation does not enforce "exactly one" — zero, one, or several may appear.
  • Maps to plain optional protobuf message fields.

B · Mutually-exclusive union wire-safe oneOf

Event:
  type: object
  properties:
    cat_event: { $ref: '#/.../Cat' }
    dog_event: { $ref: '#/.../Dog' }
  oneOf:
    - required: [cat_event]
    - required: [dog_event]
  • Same properties; the oneOf constrains which one key must be present.
  • Validators enforce "exactly one." Maps to a protobuf oneof.
  • No discriminator. The key is the tag.
Why style B is a wire-safe use of oneOf. Unlike the discriminated form, this oneOf does not flatten anything — it lists required constraints over the same named, nested properties. The wire shape stays {"cat_event":{…}}, identical to style A, and is fully protobuf-representable. The distinguishing test is mechanical: a oneOf with a discriminator is the prohibited flat form; a oneOf of required over existing object properties (no discriminator) is the supported nested form.

4. The one prohibited style

❌ Discriminated / flattening oneOf PROHIBITED

Event:
  oneOf:
    - $ref: '#/.../CatEvent'
    - $ref: '#/.../DogEvent'
  discriminator:
    propertyName: type
    mapping: { cat: ..., dog: ... }
↓ produces the flat shape protobuf can't ↓
{ "type": "cat", "pet_name": "Whiskers" }

This is the §1 form. A top-level oneOf of $ref variants plus a discriminator hoists each variant's fields to the top level, which no protobuf oneof serialization matches. It is the only union form DUH rejects.

5. How each maps to protobuf

OpenAPI inputDiscriminator?JSON wireProtobuf mappingStatus
Optional $ref properties (style A) n/a {"cat_event":{…}} optional message fields SUPPORTED
oneOf of required over properties (style B) No {"cat_event":{…}} protobuf oneof SUPPORTED
oneOf of $ref + discriminator Yes {"type":"cat",…} flat none possible PROHIBITED
allOf n/a flat merge no merge concept — ambiguous numbering PROHIBITED
anyOf n/a arbitrary subset no equivalent PROHIBITED

allOf/anyOf are prohibited for a different reason than the flat oneOf: not JSON-wire divergence but schema-to-proto mapping ambiguity (no protobuf merge or "one-or-more" concept, ambiguous field numbering).

6. The proof VERIFIED 100%

The claim "nested unions are wire-compatible" is not a spec reading — it was verified end-to-end with the actual protobuf toolchain (protoc 23.4, protoc-gen-go, and google.golang.org/protobuf/encoding/protojson — the exact marshaler duh.go uses, at its bare defaults). The harness lives in docs/oneof-wire-proof/ and is re-runnable.

It compiles two protobuf encodings of the same union — a real oneof and plain optional fields — with a multi-word snake_case field (pet_name) to catch the casing trap, then asserts:

$ go test -v ./... === RUN TestOneofAndOptionalProduceIdenticalWire oneof form -> {"cat_event":{"pet_name":"Whiskers"}} optional form -> {"cat_event":{"pet_name":"Whiskers"}} --- PASS // both proto encodings → identical nested JSON, snake_case preserved --- PASS: TestDogVariantWire // other variant identical --- PASS: TestCrossUnmarshal // oneof-server bytes read by optional-client, and reverse --- PASS: TestGenericJSONConsumerInterop // plain encoding/json (OpenAPI-side) reads/writes same shape --- PASS: TestProtoOneofEnforcesExactlyOne // real oneof rejects two-variant input; optional accepts --- PASS: TestNeitherSetWire // empty case → {} on both --- PASS: TestBinaryWireAlsoCompatible // BINARY protobuf wire identical too: 0a 0a 0a 08 ... PASS

The casing trap — closed

protojson's default would emit "petName" for a field named pet_name. openapi-schema.go always writes an explicit [json_name = "pet_name"], which protojson honors — so snake_case stays byte-identical on both wires. The proof models this and confirms "pet_name", not "petName".

Exactly-one, for free

A real protobuf oneof rejects JSON with two variants set ("oneof … is already set") — matching style B's oneOf semantics. For every valid (single-variant) value the wire is identical; the forms only diverge on invalid input. This is why style B maps cleanly to a protobuf oneof.

7. Implementation status

Style A works today. Style B (the wire-safe oneOf) is proven compatible but not yet accepted by the toolchain — these are the gates that must change together. The linter and the converter are two independent gates; loosening only one moves the failure rather than fixing it.

ProjectTodayChange to support style B
openapi-schema.go Errors: validateTopLevelSchema requires a discriminator on any oneOf. Recognize the oneOf-of-required pattern (no discriminator, branches are required over existing properties); emit a protobuf oneof over those fields; treat the constraint as validation-only.
duh-cli PROHIBITED_ONEOF fires on len(OneOf) > 0 — any keyword use. Narrow the rule: prohibit only oneOf with a discriminator (the flat form); allow oneOf-of-required over object properties.
duh.go Marshals with bare protojson defaults. No change required — proven compatible as-is (§6).

8. Rules of thumb

  • Want a union? Give each variant its own optional $ref property (style A). The key is the tag; the payload nests.
  • Want "exactly one" enforced? Add oneOf: [{required:[a]},{required:[b]}] over those properties (style B). Still nested, still wire-safe.
  • Never use oneOf + discriminator, or allOf/ anyOf — those can't be honestly served over both wires.
  • The mechanical test: oneOf + discriminator = flat = banned. oneOf + required over named properties = nested = fine.
