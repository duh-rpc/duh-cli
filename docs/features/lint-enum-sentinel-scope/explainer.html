Making the ENUM_UNSPECIFIED_VARIANT rule mean something again

duh lint rejects enums that duh generate happily accepts. Authors have learned to silence the rule — which means it no longer protects anyone. This change narrows the rule to fire only where the generator actually constrains you, and adds a gentle nudge for the one mistake that started it all.

ENG-73 ADR 0004 · 0007 · 0010 scope: internal/lint/rules no generator changes

TLThe short version

One rule gets narrower, one new advisory warning gets added, and lint stops disagreeing with generate.

TODAY

The error fires on every enum whose first variant isn't named *_UNSPECIFIED — even string enums and numeric enums where that's impossible or meaningless. The only escape is to disable the rule.

AFTER

The error fires only on an integer enum that declares an *_UNSPECIFIED sentinel in the wrong spot — exactly what the generator rejects. A separate WARNING catches the "wrong type" mistake without blocking anything.

1The problem today

The rule was written for an older version of the conversion library, where every OpenAPI enum — string or integer — became a Protobuf enum. In a Protobuf enum, wire number 0 is the default for an unset field, so reserving it for an *_UNSPECIFIED sentinel keeps "unset" distinguishable from a real value. Requiring that sentinel first made sense.

Then the library changed (commit 55eb0d7): only integer enums become Protobuf enums now. String enums generate a plain, open proto string field. The lint rule never caught up — so it now fires on cases that have no number 0 to protect and that duh generate accepts without complaint.

Case A — the ticket: a perfectly valid string enum

openapi.yaml
SeekStart:
  type: string
  enum: [earliest, latest, at_offset]   # open string field — any string is valid on the wire
today
$ duh lint openapi.yaml
[ERROR] [ENUM_UNSPECIFIED_VARIANT] Enum's first variant 'earliest' is not an UNSPECIFIED variant
        Suggestion: Declare an UNSPECIFIED variant (e.g. STATUS_UNSPECIFIED) as the first enum entry…

# …but duh generate accepts this exact spec. The suggestion is impossible to satisfy
# meaningfully — there is no proto enum here, and no number 0.

Case B — a legitimate numeric enum the check can't even express

openapi.yaml
HttpCode:
  type: integer
  enum: [200, 404, 500]          # a real proto enum; 200 legitimately owns number 0
today
$ duh lint openapi.yaml
[ERROR] [ENUM_UNSPECIFIED_VARIANT] Enum's first variant '200' is not an UNSPECIFIED variant

# The variants are numbers. No number can end in "UNSPECIFIED".
# The rule is literally unsatisfiable for this valid enum.
The consequence: because the error can't be satisfied, teams reach for --disable ENUM_UNSPECIFIED_VARIANT or per-schema x-duh-lint-ignore. Once a rule is routinely disabled, it stops protecting the one case it was meant to protect. That broken trust — not any single false positive — is the real defect.

2The mental model that fixes it

DUH projects an OpenAPI enum to Protobuf in exactly two ways, and the type field is the switch. The sentinel only matters in one of the three shapes below.

OpenAPI declaration Generates Sentinel
relevant?
type: string + enum: [earliest, latest] Open proto string field. Any string is valid on the wire (AIP-126 "may grow"). No
no proto enum, no 0
type: integer + enum: [200, 404, 500] Closed proto enum; first value → number 0 (CODE_200 = 0), any name. No
0 holds a real value
type: integer + enum: [CODE_UNSPECIFIED, CODE_OK, …] Closed proto enum keyed by literal value; the sentinel owns number 0. Yes
the only shape

So the two real authoring modes a contract author chooses between are:

Open string enum

type: string + enum. The set may grow; the wire carries the literal string. No sentinel, not locked.

Closed proto enum

type: integer + named variants with *_UNSPECIFIED first. Wire-safe: number 0 means "unset," so an absent field never decodes as a real value (ADR 0004).

3The experience after the change

Same specs, run through duh lint once this ships.

A  The ticket's string enum — now silent

after
$ duh lint openapi.yaml   # type: string, [earliest, latest, at_offset]
✓ compliant        # exit 0 — the rule no longer touches string enums

B  The numeric enum — now silent

after
$ duh lint openapi.yaml   # type: integer, [200, 404, 500]
✓ compliant        # exit 0 — a bare integer enum legitimately puts a value at 0

C  A genuinely wrong proto enum — still caught, better worded

openapi.yaml
Code:
  type: integer
  enum: [CODE_OK, CODE_UNSPECIFIED]   # sentinel declared, but NOT first
after
$ duh lint openapi.yaml
[ERROR] [ENUM_UNSPECIFIED_VARIANT] Enum declares an *_UNSPECIFIED sentinel but its first variant is 'CODE_OK'
        Suggestion: Move the *_UNSPECIFIED variant to the first position so it owns
        Protobuf number 0 (the wire default for unset)

# This is exactly the spec duh generate rejects. Lint and generate finally agree.

D  The "wrong type" mistake — a new, non-blocking nudge

A type: string enum with sentinel-style names is almost always an author who meant a closed proto enum and reached for the wrong type. The new ENUM_STRING_SENTINEL_NAMES warning points that out — but never fails the build.

openapi.yaml
Status:
  type: string
  enum: [STATUS_UNSPECIFIED, STATUS_ACTIVE]   # proto naming on a string enum?
after
$ duh lint openapi.yaml
[WARNING] [ENUM_STRING_SENTINEL_NAMES] String enum variant 'STATUS_UNSPECIFIED' uses proto-enum
        sentinel naming, but a string enum generates an open proto string field
        Suggestion: For a closed, wire-safe proto enum use type: integer with named
        variants; to keep an open string field, drop the *_UNSPECIFIED sentinel
✓ compliant        # exit 0 — a warning is guidance, not a gate

4The invariant that keeps it honest

The whole point is lint ↔ generate parity: duh lint must reject exactly the enum specs duh generate rejects, and accept the rest. The generator (via fieldmap.assertUnspecifiedFirst) hard-errors in exactly one situation — an enum that declares an *_UNSPECIFIED sentinel which isn't its first variant.

shared predicate
strings.HasSuffix(value, "UNSPECIFIED") — the same definition of "is a sentinel" in both the lint rule and fieldmap.
shared test
"sentinel present but not first" — the same first-position check on both sides.
result
A spec passes lint iff it passes generate. The disagreement that forced the workarounds is gone.
Known trade-off: parity rests on that predicate being duplicated identically in two packages, by convention rather than a shared symbol. Change one without the other and parity silently breaks. A future refactor could export a single predicate consumed by both — noted as future work, not done here.

5What's in, and what's deliberately out

In scope

  • Re-scope ENUM_UNSPECIFIED_VARIANT to integer enums with a misplaced sentinel; reword its message in OpenAPI terms.
  • Add the ENUM_STRING_SENTINEL_NAMES advisory warning.
  • Rewrite the rule's test to the new model (surface tests via RunCmd).
  • Remove the now-redundant --disable and x-duh-lint-ignore workarounds from the fieldmap-lock tests.
  • Reconcile the docs: CONTEXT.md "Seeding" entry and ADRs 0004/0007.

Out of scope

  • No change to duh generate or the openapi-schema.go library — lint is brought in line with the generator, not the reverse.
  • No new "closed string enum" feature. type: string stays open; the closed path stays type: integer.
  • The warning trigger stays narrow — only string values ending in UNSPECIFIED, not all SCREAMING_SNAKE_CASE (too noisy).
  • Downstream services/demo and services/slip-stream specs resolve when they pick up the rule change.
